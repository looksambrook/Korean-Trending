# B1/B2/B3 실험 설계 초안 v0.1

작성일: 2026-09-11. 상태: **실행 전 설계**. 실제 LLM 응용문 생성·사람 평가·효과 추정은 아직 수행하지 않았다. 로컬 요청 생성과 `smoke_fixture` 점검은 실험 성능이 아니다. 목표 시점은 2026년 12월 전이고 평가 대상은 주로 20대다. 평가자는 연구자 제외6명이상 확보 가능이라고 답했으며, 모델·예산·실제 참여 수·투고처는 미정이다. 단계별 날짜는 실행 계획의 제안이며 실험 완료를 보장하지 않는다.

## 1. 주 질문과 분석 대상

같은 LLM이 같은 계열 원문과 지원 용례를 사용할 때, 보존 요소·변경 가능 요소·사용 맥락을 명시적으로 제공하면 상황 적합성과 밈 정체성 보존이 개선되는지 평가한다. 주실험은 **계열이 이미 주어진 상황에서 응용문을 생성하는 과제**다. 계열 선택 또는 검색은 개입하지 않는다.

평가 단위는 `(family_id, scenario_id, condition, repeat)`의 생성 결과다. 같은 상황의 조건별 결과를 짝지어 비교하며, 같은 계열 안의 상황과 평가자는 독립 표본 수로 부풀리지 않는다. `query_id`와 `generation_replica`는 각각 상황 ID와 반복 번호를 설명하는 별칭이며 실제 저장 키는 `scenario_id`, `repeat`다. 생성 반복 수는 실행 전 확정하고 모든 조건에서 맞춘다. 기본 파일럿은 출력 후보 한 개로 요청 형식을 점검하되, 본실험 반복 수를 이미 확정한 것으로 보지 않는다.

## 2. 조건과 인과적 해석 범위

모든 조건은 동일한 상황, 목표 계열, 원문, 지원 문장 및 지원 문맥을 같은 순서로 받는다. 공통 시스템 지시와 생성 요청의 목표·출력 형식을 유지하고 추가 정보 구역만 달리한다.

| 조건 | 입력 | 주 해석 |
|---|---|---|
| B1 원자료 | 공통 입력 | 원자료만으로 같은 기반 모델이 수행하는 기준선 |
| B2 서술형 | B1 + 동일 자동 레코드의 사실을 고정 규칙으로 문장화한 설명 | 자동 추출 정보를 제공하되 필드 묶음 대신 서술형으로 제공 |
| B3 필드형 | B1 + 동일 자동 레코드를 필드별로 표시 | 제안한 구조·사용 맥락 표현을 제공 |

**B3−B1**은 자동 추출·정보 추가·표현 방식이 포함된 전체 방법의 차이다. JSON 형식만의 효과라고 해석하지 않는다. **B3−B2**는 같은 자동 추출 정보의 표현 방식을 달리한 차이이며 핵심 통제 비교다. **B2−B1**은 서술형으로 제공한 자동 추출 정보 추가의 차이로 보조 분석한다.

완전히 같은 토큰 수와 동일한 인지적 정보량을 동시에 보장하기는 어렵다. 사실 항목의 대응은 검증하고 각 조건의 실제 입력 토큰·문자 수·출력 토큰을 기록한다. 토큰 수를 맞추려고 원자료를 조건별로 다르게 자르거나 무관한 문구로 채우지 않는다. 모든 조건이 문맥 창에 들어오도록 전체 묶음을 사전에 확인한다.

## 3. 추출 및 렌더링

1. 계열 원문과 허용 지원 자료만으로 자동 레코드를 한 번 추출한다. 평가 상황·평가 정답·평가 결과를 추출 입력으로 사용하지 않는다.
2. 원응답, 파싱 결과, 오류·재시도, 모델과 프롬프트 버전, 입력 해시를 저장한다. 자동 레코드는 사람이 의미를 수정하지 않는다.
3. 검증을 통과한 동일 레코드에서 B2와 B3를 만든다. 두 조건의 레코드 ID와 해시가 같아야 한다.
4. B2는 별도 LLM에게 자유 요약을 시키지 않는다. 각 필드의 모든 원자 사실, `evidence_ids`, `certainty`, 불확실성 및 빈 목록을 정해진 한국어 문장 틀과 순서로 렌더링한다. B3도 같은 필드를 같은 순서로 표시한다.
5. 값·근거·확실성의 누락, 추가, 의미 변형이 없는지 필드 대응을 기계 점검하고 개발 자료에서 사람이 읽어 확인한다. 렌더러를 잠근 뒤 시험 결과를 보고 문장 틀을 수정하지 않는다.
6. 추출이 실패한 계열은 실패 상태를 남긴다. 사람이 레코드를 작성해 자동 결과로 대체하지 않는다. 재시도 횟수와 형식 오류 처리 규칙은 실행 전에 고정한다.

`form_labels`, `functions`, `preservation_constraints`, `editable_elements`, `adaptation_modes`, `usage_context`, `modality_dependency`, `uncertainty_notes`는 각기 원자 사실 목록이다. 변경 요소가 없는 인용·말투·대화형에서도 빈 목록과 관련 보존·응용 규칙을 전달한다. 모든 계열에 치환 슬롯을 만들어 넣지 않는다.

## 4. 실행 공정성과 기록

- 기반 생성 모델 ID·버전, 공통 시스템 지시, 온도, top-p 등 사용 파라미터, 최대 출력 길이, 호출 날짜, seed 지원 여부를 기록한다. API의 비결정성을 seed만으로 제거했다고 주장하지 않는다.
- 실행 순서는 조건·상황에 걸쳐 무작위화 또는 균형 배정하고 seed를 저장한다. 시간에 따른 API 변경을 피하기 위해 가능한 한 동일 실행 구간에 처리한다.
- 각 조건에 같은 수의 생성 기회를 준다. 좋은 출력만 고르거나 특정 조건만 재생성하지 않는다. 네트워크·형식 재시도와 품질 개선을 위한 재생성을 구별한다.
- 추출 모델과 생성 모델이 다르면 각각 기록한다. 생성 모델은 B1/B2/B3에서 동일해야 한다. 현재 설정은 하나의 `model_id`를 추출·생성에 공통 사용하며 별도 추출 모델 설정은 아직 구현하지 않았다.
- 별도 검증기, 재순위화, 여러 후보 선택은 기본 주실험에 넣지 않는다. 추가하면 호출 수·후보 수 차이를 통제한 별도 실험으로 명시한다.
- B1에는 구조 추출 호출이 없다. 전체 비용·호출 수가 같다고 주장하지 않는다. 계열당 일회성 추출 비용과 질의당 생성 비용을 분리하고 재사용 횟수를 명시한다.
- 입력 데이터·분할·레코드·프롬프트·설정의 해시, 실행 ID, 원출력, 파싱 상태, 토큰 사용량, 오류, 재시도를 저장한다. 로컬 점검에서 토큰화기나 가격을 확인하지 못하면 문자 수·예산 변수로만 보고한다.

## 5. 별도 참고 실험

**사람 검토 레코드:** `record_origin: human_reviewed`인 별도 조건으로 수행하는 설계 제안이다. 현재 자동 주실험 CLI에는 이 참고 조건을 실행하는 경로가 없다. 검토자가 추가한 지식과 수정 시간·과정을 공개한다. B3 자동 조건에 합치거나 자동 시스템의 성능·상한으로 부르지 않는다.

**제거 실험:** 보존·변경 정보 제거 또는 사용 맥락 정보 제거 후보를 개발 단계에서 선택한다. 다른 필드에 남아 있는 같은 정보도 함께 점검해야 한다. 시험 점수가 잘 나오는 제거 실험만 고르지 않는다.

**두 번째 모델:** 자원이 허용될 때 주요 비교의 재현성을 확인하는 선택 사항이다. 첫 모델 결과만 있으면 그 범위로 결론을 제한한다. 미세조정은 현재 기본 설계에 포함하지 않는다.

## 6. 검색·추천·전체 시스템의 별도 평가

검색은 사용자 상황으로 후보 계열을 선택하는 과제다. 복수 적합 계열과 적합성 등급을 독립적으로 마련하고, 후보 집합·지원 정보·정답 작성 절차·k를 고정한 뒤 Recall@k 또는 nDCG@k 등을 사용한다. 이 정답은 추출이나 주 생성 프롬프트 개발에 들어가지 않는다.

검색 후 생성하는 전체 시스템은 검색 성공·실패를 포함한 별도 실험으로 보고한다. 같은 계열을 고정한 주실험 결과와 표를 섞지 않는다. 검색이 좋아졌다는 결과로 생성 자체의 개선을 주장하지 않는다. 부적합한 상황에서 추천을 보류하는 과제도 별도 조건이다. 주 생성 실험은 목표 계열을 실제로 적용할 수 있는 상황을 독립적으로 작성·검토하여 사용한다.

## 7. 첫 소수 사례 파일럿의 진행 기준

첫 파일럿은 검증된 소수 계열에서 다음을 점검하는 **개발 목적의 절차 파일럿**으로 제안한다. 본실험 표본 규모나 KCI 요구량을 뜻하지 않는다.

1. 원문·실제 용례·문맥·출처가 확인되었는지, 지원의 독립성을 확보했는지 점검한다. 인용형과 비슬롯형을 포함해 형식 편중을 확인한다.
2. 데이터 검증과 요청 생성을 오프라인으로 실행한다. 합성 fixture의 출력은 데이터·실험 성과로 집계하지 않는다.
3. 소액 실행 범위를 확정한 뒤 실제 모델로 자동 추출한다. B2/B3의 정보 동일성과 근거 없는 추출의 빈도를 검토한다.
4. 별도 작성된 개발 상황으로 B1/B2/B3를 생성하고, 조건 익명화·두 단계 평가 화면·평가 시간·척도 이해 가능성을 점검한다.
5. 오류와 부담을 바탕으로 개발 지침만 수정한다. 이후 새 시험 계열, 주요 비교, 표본 수, 비용 상한, 분석 계획을 잠근다.

이번 로컬 준비는 실제 모델 호출을 하지 않는 요청 생성·응답 반입 방식이다. 준비 요청은 `execution_ready=false`로 관리하며, 원시 준비 요청 파일을 제공자 API에 그대로 보내지 않는다. 후속 `execute_responses.py`에 범위·비용·원응답 저장을 위한 개발 파일럿 어댑터를 준비했다. 실제 API 호출·사람 평가 결과는 없으며, 미승인 설정의 실행은 차단된다. 현재 실행 방법은 [v0.3 실행안](pilot_execution_v03.md)을 따른다. 현재 추출 누락·실패로 생성하지 못한 B2/B3 항목도 실패 파일과 평가 관리자용 키에 남겨 전체 계획 분모에서 지우지 않는다. 유료 대량 호출과 사람 모집은 모델·금액·평가자·절차의 범위가 확정된 뒤 진행한다. 결과가 없으므로 방향·크기·통계적 유의성에 관한 성과 문장은 아직 쓸 수 없다.

표시 언어 통제: B3의 필드명과 근거·확실성 표시도 B2와 같은 한국어 어휘로 렌더링한다. 내부 영어 스키마 키와의 일대일 대응은 content audit에 남긴다. 이 비교는 특정 서술형/필드형 렌더링 간 차이를 측정하며 모든 구조화 프롬프트의 보편적 효과로 일반화하지 않는다.
