# 주석 지침 초안 v0.1

작성일: 2026-09-11. 상태: **실행 전 제안**. 독립 주석, 합의, 일치도 측정은 아직 수행하지 않았다. 연구 범위와 확정 조건은 원본 `RESEARCH_HANDOFF.md`와 사용자 지시를 따른다. 지침의 라벨·주석자 수는 개발 파일럿에서 검토한 뒤 시험 자료를 열기 전에 고정한다.

## 1. 주석 대상과 자료의 출처

주석 단위는 동일한 원형과 핵심 사용 관습을 공유하는 **유행어 계열**이다. 실제 사용 하나는 지원 용례로 기록하며, 개별 용례에서 관찰한 사실과 계열 전체에 대한 추론을 구별한다. 동일 영상·글의 재게시 여러 개를 독립 용례 여러 개로 세지 않는다.

출처 확인과 분석의 정답성은 다르다. `verification_status: text_verified`는 출처에서 해당 텍스트를 확인했다는 의미이며, 원조·최초 사용·대중적 빈도·변경 규칙의 타당성까지 검증했다는 뜻이 아니다.

| `provenance` | 의미 | 실제 유행 사례로 집계 |
|---|---|---|
| `observed_web` | 식별 가능한 외부 출처에서 실제 사용을 수집 | 텍스트·문맥 확인 후 가능 |
| `researcher_authored` | 연구자가 만든 예문·평가 상황 | 불가 |
| `ai_synthetic` | AI 생성 또는 AI 초안에서 작성한 자료 | 불가 |
| `user_supplied_unverified` | 사용자가 제공했으나 외부 근거가 미확인인 표현 | 확인 전 불가 |

연구자가 AI 초안을 편집해도 AI 관여 이력을 지우지 않는다. 수집 용례의 요약·전사를 AI로 작성했다면 원문 위치와 변환 이력을 별도 메타데이터에 남긴다. 사용자 예시 ‘거제 야호’, ‘감옥에서 누가 돌아왔게’는 검증 전에는 범위 설명 또는 미확인 후보로만 취급한다.

## 2. 주석자가 볼 수 있는 정보

구조 주석·자동 추출은 `family_id`, `canonical_text`, 해당 계열의 허용된 지원 용례와 출처 문맥만 사용한다. 근거가 없는 원형 후보는 확정 원형으로 바꾸지 않는다. 최초 출처가 미확인이라면 그대로 기록한다.

시험 평가 상황, 평가용 응용문, 모델 생성 결과, 점수, 평가자 코멘트는 제공하지 않는다. 시험 지원 자료를 읽는 작업도 잠긴 지침으로 수행하며, 그 자료에 맞춰 프롬프트나 규칙을 고치지 않는다. 시험 자료를 보고 수정이 필요하면 새 개발 자료로 전환하고 이후 시험 집합을 새로 마련한다.

## 3. 다축 표현과 판단 기준

유형은 하나의 상호배타적 분류로 강제하지 않는다. 아래 라벨은 후보이며 관찰에 맞지 않으면 불확실성을 기록한다. 슬롯이 없는 계열은 `editable_elements: []`를 허용한다. 빈 목록은 자동으로 ‘어떤 변경도 불가능’이라는 뜻이 아니다. `uncertainty_notes`에 ‘변경 사례 없음’, ‘관찰 근거 부족’ 또는 ‘변경 요소 적용 불필요’를 구별해 적는다.

| 필드 | 기록할 내용 | 판단 기준 |
|---|---|---|
| `form_labels` | 구호, 인용문, 문장 템플릿, 말투·종결형, 대화형, 복합형 등 복수 라벨 | 표면 형식의 근거를 적는다. 사용 목적과 섞지 않는다. |
| `functions` | 복귀, 인사·등장, 공감, 놀람, 불평, 풍자 등 | 주변 문맥에서 수행한 의사소통 행위를 적는다. 단어만으로 추측한 기능은 잠정으로 둔다. |
| `preservation_constraints` | 핵심 어구·어순·질문형·반복·말투·함의·화자 순서 | 원형 인식과 기능에 필요한 요소 후보를 근거와 함께 기록한다. 관찰된 공통점을 반드시 지켜야 하는 법칙으로 과장하지 않는다. |
| `editable_elements` | 바뀐 대상·장소·행동·수량 등과 조사·어미 조정 | 실제 변형을 근거로 적는다. 일반적인 명사라는 이유만으로 슬롯을 만들지 않는다. |
| `adaptation_modes` | 그대로 인용, 단어 교체, 형태 조정, 말투 적용, 대화 재구성 등 | 관찰된 방식과 시도 가능성이 추정되는 방식을 구별한다. |
| `usage_context` | 상황, 상대와 관계, 매체, 톤, 부적합 가능 맥락 | 특정 게시물의 관찰과 계열 일반화를 구별한다. 관찰되지 않은 금기·적합 조건을 사실로 추가하지 않는다. |
| `modality_dependency` | 텍스트만 가능, 음성 도움, 동작·영상 필요, 불명 | 문자만으로 평가 가능한지 기록한다. 원영상의 존재만으로 영상 필수라고 판단하지 않는다. |
| `uncertainty_notes` | 원형 미확인, 독립 용례 부족, 경쟁 분석, 의미 중의성 등 | 불확실성 자체를 삭제하거나 평균내지 않는다. |

문장 템플릿은 여러 형식 중 하나다. 그대로 인용해야 적절한 경우, 말투를 옮기는 경우, 두 화자의 순서를 보존해야 하는 경우를 동일한 빈칸 치환식으로 표현하지 않는다. 필요하면 `preservation_constraints`와 `adaptation_modes`의 문장형 값에 화자별 발화 순서를 기술한다. 이 첫 버전은 자유 텍스트 원자 사실을 포함한 구조 표현이며, 모든 변형 규칙을 실행 가능한 문법으로 구현한 것으로 주장하지 않는다.

## 4. 근거와 불확실성 기록

각 필드는 동일한 원자 사실 구조를 사용한다.

```json
{
  "value": "한 가지 관찰 또는 해석을 담은 문장",
  "evidence_ids": ["해당 계열의 support_id"],
  "certainty": "supported"
}
```

- `supported`: 인용한 지원 용례에 해당 사실의 직접 근거가 있다. 계열 전체에 예외가 없다는 뜻은 아니다.
- `tentative`: 문맥이나 용례 수의 한계로 잠정적 해석이다. 확정 사실처럼 생성기에 전달하지 않는다.
- 근거가 없으면 사실을 만들어 채우지 않는다. 해당 필드를 비우고 불확실성을 기록한다. 근거 ID가 존재한다는 것과 그 근거가 주장을 실제로 지지한다는 것은 별도로 확인한다. 현재 검증기는 `uncertainty_notes`의 `tentative` 항목에만 빈 `evidence_ids`를 허용하고 나머지 사실에는 최소 하나의 해당 계열 지원 ID를 요구한다.
- 한 항목에 서로 다른 주장을 여러 개 묶지 않는다. B2/B3 정보 대응과 추출 오류 분석이 가능하도록 사실을 분리한다.
- 상충하는 유효 분석이 있으면 근거와 함께 모두 잠정으로 남긴다. 단일 정답을 만들기 위해 근거 없는 확정을 하지 않는다.

관찰된 동일 문자열을 보존 후보로 적을 때는 문자열과 해석을 구별한다. 예를 들어 ‘해당 어구가 지원 두 곳에서 반복됨’과 ‘이 어구를 반드시 보존해야 함’은 다른 주장이다. 후자는 추가 변형 근거가 부족하면 `tentative`이다.

## 5. 자동·사람·점검 자료 분리

| `record_origin` | 작성 과정 | 보고 범위 |
|---|---|---|
| `automatic` | 고정된 모델·추출 프롬프트로 지원 자료에서 자동 추출한 원결과 | 주실험 B2/B3의 입력 |
| `human_reviewed` | 사람이 수정·합의한 레코드 | 별도 참고 조건 및 추출 평가용 주석 |
| `smoke_fixture` | 입출력·렌더러 점검용으로 만든 레코드 | 소프트웨어 점검만; 시스템 성능 평가 금지 |

자동 레코드의 오류를 사람이 수정한 뒤 같은 실행 ID로 덮어쓰지 않는다. 원출력, 파싱 결과, 수정 레코드, 수정 이유, 관련 버전을 별도 보관한다. 사람 검토 조건은 자동 시스템 성능 또는 수학적 상한으로 표현하지 않는다. 사람 주석자가 외부 지식을 참고했다면 자료와 범위를 남기고, 지원만으로 만든 조건과 구분한다. 현재 CLI의 자동 주실험 경로는 `human_reviewed` 레코드를 거부한다. 사람 검토 참고 조건과 독립 주석·합의 관리 도구는 아직 구현하지 않았으며 위 내용은 해당 작업의 설계 지침이다.

## 6. 독립 주석 및 합의 절차 제안

1. 개발 계열로 지침을 읽고 연습한다. 논의한 자료는 이후 숨겨진 시험 자료로 사용하지 않는다.
2. 확보 가능하다면 한국어 사용 능력을 갖춘 2명 이상이 같은 지원 묶음을 독립적으로 주석한다. 인력 수·시간·보상은 연구자 확인 전 제안이다.
3. 합의 전 원주석을 보존하고 항목별 불일치 원인(정의 모호, 근거 부족, 출처 해석, 복수 가능 분석)을 기록한다.
4. 근거를 대조해 합의 레코드와 변경 사유를 작성한다. 해결 불가하면 복수 분석 또는 미정으로 남긴다.
5. 개발에서만 지침을 수정한다. `annotation_version`과 변경 이력을 고정한 뒤 시험 계열은 해당 버전으로 주석한다.

합의 후 자료만으로 일치도를 계산하지 않는다. 범주 라벨은 합의 전 라벨별 일치·분포를 보고하고, 다중 라벨 집합 유사도를 보조로 볼 수 있다. 원자 사실의 동치 판단 기준과 정렬 절차가 없으면 자유 문장 전체에 대한 단일 ‘정확도’를 계산하지 않는다. 근거 없는 주장 비율, 근거 연결의 타당성, 필요한 요소 누락, 과도한 슬롯화 등을 따로 기록한다.

문자 구간 주석이 필요해지면 Python의 유니코드 코드포인트 기준, 0부터 시작하고 끝 위치를 제외하는 `[start, end)`를 제안한다. NFC 정규화 및 공백 처리 버전을 함께 고정하며 원문은 보존한다. 이 구간 방식은 아직 필수 스키마에 포함하지 않은 확장 제안이다.

## 7. 레코드 완료 점검

- 지원 ID가 모두 실제 해당 계열의 허용 지원 자료를 가리키는가?
- 실제 수집·연구자 작성·AI 합성을 구별했는가?
- 텍스트 확인을 원조 확인이나 사용 규칙 검증으로 확대하지 않았는가?
- 형식·사용 기능·보존 요소·변경 요소를 구별했는가?
- 슬롯 없는 표현과 대화·말투 표현을 손실 없이 설명했는가?
- 지원 범위를 넘는 일반화와 미확인 사항을 잠정 또는 미정으로 남겼는가?
- 자동 원결과를 보존하고 사람 수정본의 출처를 구별했는가?
- 평가 상황·정답·출력·평가 결과가 들어오지 않았는가?
